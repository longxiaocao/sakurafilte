# R2 迁移评估报告（2026-08-16）

> 评估范围：①图片对象存储 MinIO → Cloudflare R2 迁移；②方案③"富化 JSON 预计算落 R2"（查询热路径脱离 PG）。
> 评估依据：master（39db157f）代码实况 + perf 环境（PG 55432 / MinIO 55900 / backend 55148）。

## 一、现状盘点

### 1.1 切换机制：代码已实现 ✅
- **三端抽象**：`IObjectStorage`（`SakuraFilter.Core/Interfaces/IObjectStorage.cs`）统一 minio / aliyun-oss / r2；配置 DTO `StorageConfigDto`（`Core/DTOs/StorageConfigDto.cs`），支持 `Provider = minio / aliyun-oss / r2`。
- **R2 复用 MinioStorage**：`ServiceCollectionExtensions.cs` L258-320 分发——R2 走 Minio SDK（S3 兼容），`WithSSL(true)` + `WithRegion("auto")`，endpoint 填 R2 S3 API 地址。
- **配置入口**：运维中心"存储配置"页 `/api/admin/storage/config`（`Endpoints/StorageConfigEndpoints.cs`）——查看（密钥脱敏）/ 保存 / 连通性测试（上传-读取-删除探针）。
- **保存持久化**：写入 `system_settings`（key=`storage_config`），**重启容器生效**（存储客户端是单例，无法热切换）。
- **启动覆盖**：`Program.cs` `ApplyStorageConfigOverridesAsync`——若部署环境已设 `Storage__Provider` 环境变量则跳过 system_settings 覆盖（环境变量优先于库内配置）。

## 二、图片迁移步骤（MinIO → R2）

### 前置（需用户操作）
1. Cloudflare 账号 → R2 → 建 bucket（建议与 MinIO 同名如 `sakurafilter`）+ 创建 API Token（对象读/写权限）。
2. 准备配置：Endpoint（`https://<account>.r2.cloudflarestorage.com`）、AccessKeyId、AccessKeySecret、BucketName、PublicEndpoint（如绑定自定义域）。

### 迁移流程
1. **连通性测试**：运维中心"存储配置"页选 r2 填凭据 → 测试（探针走通才算通过）。
2. **批量迁移脚本**（**必须断点续传**，本机有冻结史）：
   - 复用 `IObjectStorage.ListAsync(prefix)` 枚举 MinIO 对象 key（`products/` 前缀），游标式分页。
   - 逐个 `GetAsync` → 上传 R2；**进度持久化**（记已迁移 key 到本地文件 / PG），冻结恢复后从游标接力。
   - 建议挂在 `SakuraFilter.Cli`（已有孤儿图片清理先例）或独立 Python 脚本。
   - 70 万对象按 ~50ms/对象估算约 10 小时，可分批跑。
3. **切换**：保存 R2 配置 → 重启 backend → 验证 `Storage__Provider` 环境变量未设时走库内配置。
4. **验证清单**：
   - 前台图片 URL 可访问（图片代理端点 `/api/public/images/{key}` 走 `IObjectStorage.GetAsync`，R2 同样生效）。
   - 上传新图片 → R2 可见；删除 → 双端一致。
   - 孤儿图片清理 CLI 正常（依赖 `ListAsync`）。

### 回滚方案
- 重启前备份 system_settings.storage_config 原值；切回 minio 仅需改配置 + 重启（图片双端保留，无破坏性）。

## 三、方案③评估：富化 JSON 预计算落 R2

### 3.1 概念澄清（重要）
- **R2 是通用对象存储（S3 兼容），不限于图片**——"只处理图片"是 `IObjectStorage` 现状用途，非能力边界。
- **方案③ ≠ 把关系数据搬到 R2**：`cross_references` / `machine_applications` / `xref_oem_brand` **仍留 PG**；R2 存的是构建期**预计算好的富化结果 JSON**（即 `EnrichFromPgAsync` 每次现算的 oem_list / machine_list 快照）。
- **"脱离 PG" = 查询热路径脱离 PG**：查询改走"读 R2 JSON + 内存缓存"，PG 仅服务离线构建与管理后台 → 连接池压力、每请求 ~44ms 富化同时消失。

### 3.2 改造点
| 位置 | 改动 |
|---|---|
| 构建期 | `EtlImportService.ReindexFromIdAsync`（已有 fromId 断点续传）索引循环内，顺带把每 mr1 富化结果写 R2（key 如 `enrich/{mr1}.json`） |
| 查询期 | `MeiliSearchProvider.EnrichFromPgAsync` 改三层：读 R2 JSON（`IObjectStorage.GetAsync`）→ 内存缓存 → miss 才回 PG 现算 |
| 失效 | 写路径触发点（产品编辑 / `AdminXrefReorderEndpoints.EnqueueIndexRebuildAsync` / `OemBrandDictService.ApplyChangeAsync`）→ 删 R2 JSON + 缓存 `Remove()` |
| 配置 | 复用 `IObjectStorage` 即可，无新配置项 |

### 3.3 收益 vs 代价
**收益**
- 查询热路径彻底不碰 PG → 连接池 100 槽上限不再构成约束（容量模型变化：O(查询) 从 PG 连接变为对象存储 IO）。
- 富化延迟 ~44ms → 对象存储 + 缓存 ~1-5ms；**重启不冷**（现有 EnrichmentCache 是内存 TTL 3min，重启即空）。

**代价**
- 写路径复杂度：失效触发点 3 处 + 并发编辑竞态需处理。
- 构建期额外 IO：100 万 JSON（每份几 KB，总量 ~GB 级）写入。
- 一致性窗口：JSON 过期与 PG 实时之间需明确 SLA（TTL 兜底 or 写路径强失效）。

### 3.4 结论
- **技术上完全可行**，改造量中等（构建期 + 查询期 + 失效点，约 3 文件核心改动 + 测试）。
- **当前边际收益有限**：`EnrichmentCache`（TTL 3min）已把压测拉到 c100 P95=187ms 达标线，方案③解决的是"重启冷启动 + 极端并发下 PG 连接"问题。
- **建议**：**与 R2 迁移捆绑实现**（反正要动 `IObjectStorage` 链路），不单独立项；实现后查询彻底脱离 PG，连接池问题一并消失。

## 四、风险与注意事项
1. **机器冻结史**：迁移脚本必须断点续传 + 进度持久化；建议分批跑，单批 <5 万对象。
2. **R2 出网带宽**：本机 → Cloudflare R2 走公网，70 万对象迁移时长受上行带宽影响（10 Mbps ≈ 12+ 小时），建议挑低峰或分多日。
3. **密钥**：R2 凭据仅存 `system_settings.storage_config`（明文，内部库）或部署环境变量，严禁入 git。
4. **PublicEndpoint**：R2 需绑定自定义域或开公开读（bucket 公开策略），否则前台直读 URL 需预签名。
5. **测试覆盖**：新增 `IObjectStorage` 的 R2 集成测试（沿用 MinIO 集成测试模式，`AdminProductImageServiceIntegrationTests` 已覆盖接口语义）。

## 五、建议路线
1. **短期（可选，半天）**：用户提供 R2 凭据 → perf 环境演练：连通性测试 + 1 万对象小批量迁移 + 切换 + 验证（练熟流程，暴露环境问题）。
2. **中期（R2 迁移正式做时）**：写断点续传迁移脚本 → 全量 70 万迁移 → 切换 → 验证。
3. **捆绑项**：迁移时一并实现方案③（富化 JSON 预计算落 R2），查询热路径脱离 PG。
4. **不做的选项**：维持 MinIO + 现有 EnrichmentCache——已达标，仅当无 R2 需求时保留现状即可。
