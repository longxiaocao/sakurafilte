## 全面验证发现 typeahead 性能问题 + 修复（08:35-09:00）
- **用户要求全面验证** → 发现两个问题：
  1. **typeahead 8 字段慢**（oem-brand 2.1s / oem-no3 7.9s / machine-brand 3.2-5.2s / engine-brand 2.4s）——目标 P95<100ms，差 20-80 倍
  2. 产品详情页 1.1s（单条 SQL 仅 0.7ms，慢在别处，未深挖）
- **typeahead 根因**：8 字段全用 `EF.Functions.ILike(x, pattern, escape)` 三参重载 → EF 翻译成 `ILIKE '%q%' ESCAPE '\'` → **PG GIN trgm 索引不支持带 ESCAPE 的 ILIKE** → 15.5M 行 machine_applications 退化为 Index Only Scan 过滤 501 万行 → 3-5s。ANALYZE 无效；强制 indexonlyscan=off 后 trgm 也需 1.8s（CAT 命中 45 万行，数据病理）。
- **修复**（PublicTypeaheadService，分支 fix/typeahead-trgm → **PR #8**）：q 不含 `\ % _` 时两参 ILike（trgm 生效），含特殊字符保留三参（安全兜底）。EF 三元表达式可翻译（644/644 测试过）。
- **实测**：oem-brand 2.1s→**8ms**、oem-no2 1.0s→**7ms**、machine-model 24ms、model-name/engine-type 5ms；ESCAPE 安全路径 40-102ms 正常；aggregate 141ms 无回归。
- **已知限制**：machine-brand/engine-brand 仍慢（2-3.7s）——demo 数据 45 万行同品牌（CAT/VOLVO/CUMMINS），命中量本身巨大查询级无解；**建议字典表（distinct 预计算 + trgm）根治**，已在 PR body 注明。
- 教训：**三参 ILike 带 ESCAPE 会静默禁用 trgm 索引**（PG 文档行为），性能问题排查要 EXPLAIN 看是否走索引；typeahead 类"distinct 候选"查询应查字典表而非大明细表 ILIKE。
- **PR #8 已合并（9ad12b55）**：CI 9/9 全绿（Backend Build/e2e/OpenAPI/frontend-contract/镜像全过）→ squash 合并。修复已进 master。

## typeahead 9.9s 真凶：fallback 到明细表（10:30-11:30 续修，分支 fix/typeahead-dict 未提交）
- **PR #8 只修了三参 ILike**，但实测仍 9.9s：EXPLAIN 证实 partial GIN 索引根本没被用（应用发参数化 `field=@p`，PG 计划期无法证明 `@p='oem-brand'`，放弃 partial 索引 → 退化为 PK 范围扫描；而 dict 命中 0 时**回退 machine_applications(1550万行) 的 trgm 对 %ka% 吐 420万假阳性 → recheck 扫 1549万行 → 9.9s**，且 Distinct 结果恒为 0）。
